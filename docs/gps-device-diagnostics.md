# GPS device diagnostics (PARKS-329)

The admin dashboard loads `admin_get_gps_device_diagnostics(p_days)` for the last 7, 30 or 90 elapsed days, based on saved ride start time. The migration was applied to production on 2026-10-28 through the self-hosted `parksafe-self` MCP, with explicit user authorization. It adds only this new RPC and its execute grants; existing mobile tables, policies and functions are unchanged. PARKS-328's Edge Function deployment is still required for versioned measurement coverage.

Production schema verification found that audit `target_id` is NOT NULL. Aggregate audit entries therefore use the requesting admin UUID as their target under `gps_aggregate`; no ride is targeted. The local regression fixture now enforces the production NOT NULL constraint. After deployment, an admin invocation and its audit insertion were verified inside a rolled-back subtransaction. Anonymous and non-admin calls were verified to reject access; anonymous/PUBLIC execute is revoked and authenticated execute requires the internal admin guard. No ride data was changed and the test audit entry was rolled back.

The RPC checks `auth.uid()` and `is_admin()`, audits every successful request, uses a locked search path and revokes anonymous/public execution. It returns aggregate device/OS/app-version groups, further split by nullable battery-saver and Doze-exemption observations. No user or ride identifiers, timestamps of individual events, coordinates, tracks, crash or ANR data are returned. It does not join profiles or collect new mobile data.

Counts are scoped to saved rides in the window. Missing telemetry is shown at the top level because its device is unknown. The database's one-row-per-ride telemetry constraint prevents join multiplication. No frontend row limit truncates the aggregate.

Gap rate = rides with observed sample gaps (including dropped-gap counts) / rides with version-1 evidence and at least one comparable interval. Partial coverage is counted and separately disclosed; neither complete nor partial evidence proves absence of problems outside observations. Legacy positive heartbeat gaps are separate evidence and are never mixed into this denominator. Legacy empty arrays and missing evidence cannot establish zero failures.

Acceptance rate uses summed accepted/raw counts only where raw > 0 and 0 <= accepted <= raw. Rejection totals use only the three named numeric counters; a missing key remains unknown, not zero. Storage discrepancy compares the accepted count with the JSON array length of stored samples, without reading or returning point contents; filtering or refinement can explain a difference. Each metric exposes its own available ride count. Groups or gap denominators below five are explicitly marked as low sample size. Energy settings are observed associations, not causal attribution. Retention can reduce telemetry coverage even inside the selected window.

The view is under Analysis / GPS-minőség at `/admin/gps-diagnostics`, not on the dashboard. It loads telemetry only when that tab is open. It reuses AdminRecordBrowser's theme, toolbar, table, scroll container and pager styles for consistency with the other record lists. Native controls provide period selection, text filtering, sorting, page size and retry; filtering or sorting resets pagination. Interpretation notes are collapsed by default. No added animation or decorative assets. ENERGY 1 / RHYTHM 1 / MOTION 1.

The default table prioritizes device identity, ride count, measured gap rate and GPS acceptance rate. Acceptance uses a neutral quantitative meter without assigning an unsupported good/bad threshold. Rejection counters, measurement coverage and storage discrepancy are disclosed in each row's native “Mutatók” expander. Missing gap measurement uses a plain unknown label rather than repeating a low-sample warning on every legacy row. The low-sample warning remains on actual measured denominators and groups under five rides.

Follow-up migration `20261028210000_gps_device_user_counts.sql` was applied through `parksafe-self` MCP on 2026-10-28 with explicit user authorization. It adds distinct telemetry account counts per group (`users`), among rides with gap measurement (`measured_users`), and among measured rides with gaps (`gap_users`). The main list shows contributing account count below ride count; the expanded row shows measured/affected account counts. These are distinct account IDs, not verified real people or physical device counts, and are not additive across groups. No account identifiers are returned. Older RPC responses show that user count is unavailable instead of inventing zero. Local SQL tests verify six rides from one account, then two accounts with only one affected by a gap. Production invocation verified the added counts and count invariants inside a rolled-back audit subtransaction; anonymous execution remains revoked.

Verification: local PGlite executes the actual migration/RPC with anonymous, user and admin cases, known counts, legacy NULL evidence, audit and execute grants. Static React rendering verifies empty/unknown/low-sample output and the allowlist of rendered fields. No production test data is inserted. Browser/native visual verification has not been performed.
